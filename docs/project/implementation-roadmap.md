# 资金AI 3.0 近期落地路线

## 1. 文档目的

本文档用于明确从当前阶段推进到资金AI 3.0 的近期落地路线。  
重点回答：未来 3 个月内，哪些先做，哪些后做，哪些先不要做。

---

## 2. 总体推进原则

### 2.1 自动化优先
能自动闭环的能力优先做自动闭环，不默认每个节点都人工确认。

### 2.2 先立治理边界，再扩自动化范围
先把接入边界、审计、确认、回退、状态流转立住，再逐步扩大自动执行比例。

### 2.3 先做高收益、低争议、可观测能力
先落地那些：
- 价值明确
- 边界清晰
- 风险可控
- 易于结构化输出
- 便于接前端展示和追踪
的能力

---

## 3. 未来 3 个月建议节奏

## 3.1 第 1 阶段：统一入口与状态承接
重点目标：
- 助手聊天作为主要操作入口
- 默认盘、异常提醒、待确认三类基础承接区先立住
- 统一状态事件格式
- 前端与后台建立稳定状态回推链路

本阶段建议先做：
- 默认盘展示
- AI 助手统一入口
- 资金缺口监控结果承接
- 报价监控结果承接
- 对手推荐结果承接
- 询价 / 交易过程状态展示
- 异常提醒
- 待确认展示

本阶段暂不追求：
- 复杂自治
- 大规模智能体拆分
- 复杂前端产品化打磨

---

## 3.2 第 2 阶段：能力注册与治理协议
重点目标：
- 统一 tool / service 注册方式
- 统一 schema
- 统一权限、超时、重试、审计、版本协议
- 统一事件回传结构

本阶段建议产出：
- tool 注册协议
- 能力目录
- 统一调用封装
- 审计日志模型
- 失败与重试标准
- 人工确认节点协议

---

## 3.3 第 3 阶段：主流程编排试点
重点目标：
- 选择 1~2 条主流程做编排闭环试点
- 验证“自动推进 + 异常抬人 + 人工确认后恢复执行”链路

优先建议流程：
- 资金缺口开始的主流程
- 询价交互相关流程

本阶段建议重点验证：
- 状态持久化
- 失败恢复
- 事件回流前端
- 人工确认后继续执行
- 回退与审计

---

## 3.4 第 4 阶段：执行链路稳态化
重点目标：
- 把执行类能力与分析类能力分区治理
- 强化生产托底能力
- 打通 API 网关 -> 机器猫 / 数据接口的稳定链路

本阶段重点建设：
- 监控
- 限流
- 熔断
- 回放
- 回退
- 高可用
- 灾备预案

---

## 4. 近期建议先做的事

- 前端统一入口与状态承接
- 默认盘 / 聚焦区 / 异常提醒 / 待确认区的基础骨架
- tool / service 注册与治理协议
- 事件流与状态回推
- 资金缺口主流程编排试点
- 询价交互主流程试点
- 人工确认与恢复执行机制
- 审计、监控、回退链路

---

## 5. 近期明确先不要做的事

- 不先做通用大而全 Agent 平台
- 不先做过度复杂的多智能体体系
- 不先把所有模块都改造成 agent
- 不在 L3 高风险执行场景直接放开云端模型
- 不在治理边界不清时放开自动执行
- 不先花大量精力做 UI 精细化打磨

---

## 6. 验收口径

近期路线的验收重点不应是“功能数量”，而应是：

- 是否形成统一入口
- 是否形成稳定状态流
- 是否具备异常抬升能力
- 是否具备待确认处理能力
- 是否具备回退能力
- 是否形成 1~2 条可跑通的主流程闭环

---

## 7. 一句话结论

近期 3 个月的合理路线，不是追求一次性做出完整 3.0，而是先把：
**统一入口、状态承接、编排试点、人工确认、审计回退**
这几个关键骨架立住，逐步逼近“自动闭环优先、异常/待确认才人工介入”的目标态。
